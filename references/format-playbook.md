# 格式与骨架

格式不是“人味开关”。它只能把材料原本的关系摆到读者找得到的位置。

## 先认体裁

- **RFC / 设计讨论**：常见形状是背景很短、提议很具体、后面跟限制和 open questions。保留作者在讨论什么，不必补一个漂亮结论。
- **README / 发布说明**：安装条件、已知失败、版本状态和求反馈可以挨在一起。步骤要能复制，其他段落不必等长。
- **接口 / 架构**：边界、参数、状态、失败条件和调用例子是主干。说明段可以删，契约块不能拿来做装饰。
- **会议 / 聊天 / 日志**：说话人、时间和顺序本身就是证据。不要把建议改成决定，把待办改成已经完成。

## 允许发生的结构变化

根据材料选一两个，不要按清单凑数：

- 合并重复标题，删掉只换说法的摘要；
- 让一段原话或一个失败例子单独占一段；
- 把比较确实需要的内容留在表格，其他内容还原成普通段落；
- 把一串均匀列表改成“一个长项 + 两个短项”，前提是粒度本来就不同；
- 把未决项放到它实际影响的接口旁边，而不是统一堆在文末；
- 保留原文有的编号、地址、补丁格式和复现命令。

这些不是固定动作。完全不加引用块、TODO、旁注或新标题也可能是正确结果。

## 反表演检查

如果删掉新增标题和括号，正文就失去意义，说明格式在替内容装作者。把格式换到另一篇材料上仍然成立，说明它太像配方。出现“先说清楚”“先记一下”“这里故意”这类为了显得不 AI 的话，直接删掉，回到事实和协作动作。
